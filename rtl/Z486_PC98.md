# Experimental z486 backend

The opt-in `-Cpu z486` build replaces the ao486 processor with nand2mario's
z486 while retaining Zet98's PC-98 peripherals, JT08 OPNA, PCM86, legacy
SDRAM fabric and optional 64 MB extended-memory map. This is a 486-class
integer processor, not a Pentium implementation. x87 is disabled.

The latest hardware-tested candidate is #138 at **90 MHz / 64 MB**, with
JT08, PCM86, native HDD boot and upper conventional instruction caching.
Upper-address CPU checksums, RAM64, FM IRQ and Rusty's OPNA detection pass;
all four saved diagnostic disks preserve unrelated data. Speech pitch still
needs a listening comparison. #137R3 at 75 MHz remains the previous fallback.
#138 misses setup timing by 6.750 ns, within the owner's experimental limit;
hold/recovery/removal pass. These tests do not establish timing closure or
reliability on every board. The earlier 100 MHz #135 corrupted saved files
and remains rejected. See HARDWARE_TESTING.md.

The vendored configuration has an 8 KB instruction cache and an 8 KB data

does not cover the recovered `ucode.hex` image. The other upstream notices
are retained. `UPSTREAM.json` records local modifications.

## PC-98 integration

`cpu/z486_pc98_adapter.sv` connects the unified z486 bus to the already
tested 32-to-16-bit memory bridge and native PC-98 I/O bridge. Byte lanes
are preserved for odd-address and wide I/O. Two INTA transactions return
the PIC vector on the second transaction. A20 and CPU-only reset retain
the established F0/F2/F6 PC-98 implementation in `pc98_ao486.sv`.

The common wrapper keeps its existing name to preserve VHDL bindings and
memory/DMA wiring. Only the selected CPU's QIP is compiled; z486 and ao486
have colliding internal module names and must not be compiled together.

Memory writes complete at the physical fabric before the z486 external
bus accepts completion. This orders aliases and peripheral access. The
CPU's internal store queue still operates normally. Read cache lines use
four DWORD response beats through the existing memory bridge.

By default, only fixed RAM below 80000h and the configured extended-memory
aperture are cacheable, excluding the existing F00000h-FFFFFFh hole. `PC98_EXT_RAM_MB`
follows the wrapper's 0/16/64 MB setting, so posted-store forwarding cannot
make absent extended RAM appear writable. Upper conventional data accesses,
ROM and VRAM bypass caching. The native z486 VGA exclusion
also remains in force. Fast cache probes use the same PC-98 exclusions.
Instruction fetches outside cached RAM still return a complete aligned
16-byte line; repeating one DWORD would corrupt BIOS instruction fetch.

External DMA and writes through aliases request full cache invalidation.
Each cache drains its accepted transactions, blocks new cache requests,
then clears tags using its existing reset sweep. The data cache drains
posted stores; the instruction cache discards remembered CPU patch data.
No architectural CPU reset is used to invalidate caches.

The experimental `-UpperRamICache` option additionally caches instructions
at 80000h-9FFFFh only while the bank policy confirms native RAM. Upper RAM
data accesses remain uncached. A completed direct CPU store invalidates its
instruction line; bank changes, alias writes and DMA use the existing full
flush and also discard speculative fetch state. Non-native banks bypass the
instruction cache. This option needs hardware qualification for each build.

PC-98 mode disables the paging unit's early demand-request admission and
uses the existing registered `PG_MEM_TLB` stage. This breaks the live
execution-address/TLB/cache-policy/acceptance feedback path. Upstream's
early path remains enabled by default outside PC-98 mode. Fast cache
probes and instruction prefetch are unchanged.

## Validation and build

`tests/run-z486.sh` uses the existing CPU smoke, cache-coherence and 64 MB
protected-mode assembly tests against the actual replacement CPU and
PC-98 bridges. `z486_pc98_cache_tb.sv` additionally tests uncached BIOS
lines, RAM hits, bank/VRAM freshness and DMA invalidation during fills.

Simulation passed in `simulation-20260923-050137-8391e3`: BSWAP, odd/wide
I/O, unaligned data, REP MOVSD, interrupts/IRET, A20, CPU reset,
self-modifying and DMA-modified code, VRAM/stack checksums and 64 MB
protected-mode access with execution from DDR. The logs' legacy testbench
labels say ao486; `ZET98_Z486` selects z486 for this run.

Example trial build:

```powershell
./scripts/build.ps1 -Cpu z486 -SystemClockMHz 90 -ExtendedRamMB 64 `
  -SoundBoard PC9801_86 -OpnaBackend JT08 -UpperRamICache -RawIde -MidiUart -StartOnly
```

The ao486 `-LowMemoryCache` switch does not apply to this backend; z486
has its own caches. `-UpperRamICache` controls their upper instruction policy. Fitted area, timing and actual
MiSTer behavior must be checked independently of simulation. Build #116 compiled successfully at 100 MHz: 37,815/41,910 ALMs,
498/553 M10Ks and 45/112 DSPs. Its worst setup slack is -7.695 ns; this
is within the owner's experimental -12 ns allowance but is not timing
closure. The initial CPU diagnostic and repeated CPUBENCH boots stayed
black on the actual MiSTer. The unchanged ao486 baseline was restored and
reproduced 55.72.

Post-fit analysis identifies CPU-internal source/shift/store paths, with a
worst 17.137 ns data delay at a 10 ns clock period. The private-firmware
startup probe executes the reset vector and BIOS video initialization in
simulation, but mocks peripherals and is not a complete-machine boot test.
A 50 MHz diagnostic was built to distinguish timing from integration.
Build #118 synthesized but failed routing (36,430 ALMs, 496 M10Ks); it
produced no RBF. Build #119 applies the upstream production packing options
and the extra routing/physical-synthesis settings at 50 MHz as well as at
100 MHz. It fits in 36,020 ALMs and 496 M10Ks. CPU timing passes; two HDMI
setup violations remain, worst -1.561 ns. On the actual MiSTer it passes CPU
checksums, the 64 MB physical-map probe, FM timer IRQ12 and Rusty's OPNA
detector. CPUBENCH v0.980 reports 60.08 / 1.15 seconds in two runs at 50 MHz.

Build #120 retries 100 MHz with the successful packing settings and a
registered shift operand source selector. The selector uses the existing
microcode lookahead and clock enable, preserving execution latency. A
simulation assertion compares it to the original decode. The expanded
regression covers 8/16/32-bit shifts, rotates, carry flags, zero/masked
counts, SHLD/SHRD, bit scans and signed memory bit indices. All integration
tests pass in `simulation-20260923-070408-651734`. Build #120 fits in 37,279
ALMs with worst slack -8.681 ns, but the actual CPU diagnostic stalled after
the DOS banner and CPUBENCH did not boot. No 100 MHz z486 score is available.
Restoring build #119 reproduced 60.08 / 1.15 seconds on the same MiSTer.

Build #120's worst CPU path runs from the live execution address through
TLB lookup and cache admission back to paging state: 17.873 ns data delay
over 16 logic levels. Build #121 uses registered demand requests to cut
that path. Its integration regression passes in
`simulation-20260923-074732-ac51c5`: the ALU kernel remains 5,348 cycles;
RAM copy rises from 4,179 to 4,433 and stack from 2,144 to 2,277 cycles.
Build #121 also disables register packing specifically on the video line
counter crossing to allow hold-delay repair. It fits in 37,494 ALMs and
496 M10Ks, worst slack -7.167 ns. All reported hold checks now pass; the
fitter added 2.259–2.690 ns to the targeted line-counter paths. The hardware
still fails: the CPU diagnostic stalls at the DOS banner, and DOS 6.20
reports an unavailable extended-memory driver followed by divide by zero.
The unchanged build #119 was restored and again reproduced 60.08.

Build #122 prereads both forwarded GPR operands alongside the
existing microcode stage, cutting register selection and partial-load
merging out of the barrel-to-SIGMA path. Assertions compare each consumed
preread value to the former live operand. The expanded architectural
regression includes immediate load-to-shift/bit-test dependencies and
consecutive shifts. Build #121's complete timing reports identify that
path at 16.539 ns over 13 logic levels. The expanded regression passes in
`simulation-20260923-083429-421d52`, with unchanged kernel cycle counts.
Build #122 fits in 37,227 ALMs, 496 M10Ks and 45 DSPs. All hold checks pass,

checking through instruction-chain selection to the microcode ROM address.
On hardware both the CPU diagnostic and CPUBENCH remain black, with UART

It passes the CPU, 64 MB map, FM IRQ and OPNA detection tests on hardware,

The next candidate splits segment-limit comparison into parallel byte

Build #126 replaces the remaining short subtract/borrow size check with

`-Z486DebugUart` (z486 only; omit `-MidiUart`) emits atomic snapshots over
HPS UART at 115200 baud. Each line is Z followed by 32 hex digits:
EIP, physical bus address, last I/O address/data, completed transaction
count and flags. It is disabled in normal builds and does not change JT08.
The retained hardware baseline is JT08 build #115: CPUBENCH v0.980,
30,000 loops, score 55.72 in 1.24 seconds at 100 MHz / 64 MB.


The MiSTer wrapper now fixes CPU execution to the full compiled clock (90 MHz
in the current hardware profile) and removes the runtime speed menu. Saved
status bits 29:28 remain reserved and are ignored. The earlier 60/30 MHz
equivalent selections stalled DOS on hardware; 15 MHz was never qualified.
The underlying CPU throttle and its unit tests remain for upstream compatibility,
but its input is constant in the production top. Confirm removal of the throttle
in synthesis before claiming area savings. The prior fitted throttle block used
44.6 ALMs; the complete build's area delta is not yet measured.

`scripts/build.ps1 -RegisterPacking Normal` selects normal global register
packing for a controlled density experiment; the default remains `SparseAuto`.
Both retain high-performance effort, the FEC/video per-instance packing
protections and all timing checks. The build records `register-packing.txt` and
`cpu-execution-rate.txt`; normal packing still needs synthesis, timing and
hardware qualification. No sound, cache, graphics or MIDI feature is removed.

Load write-back ordering fix (B163, hardware tested: original Doom I plays): a hardwired ROM load's deferred GPR token
(`recipe_memory_write`) stays valid through stalled cycles and rewrites OPR_R
until `pipeline_advance`. The successor's VIPT `load_wb` could commit the same
register in that cycle, but was assigned first, so the older value won. In
`mov eax,[abs]; add eax,[ebp-20h]` EAX kept the MOV value. Upstream z486 has
the same order; PC-98 load staging makes the overlap reachable. The data unit
now commits and forwards `load_wb` after the memory token. Original PC-98
Doom (Watcom C 9.x) compared its sprite-frame counter against sprite 0's frame
count in R_PrecacheLevel, walked past a two-frame table into the next zone
header and exited with `W_CacheLumpNum: 19781` (the low word of ZONEID plus
firstspritelump). `tests/run-z486-rmw-reload.sh` reproduces it without Doom.

Deferred-token and optimistic-read fixes (B164): B163 still drew Doom I's
floors and ceilings wrongly. The differential fuzzer (`tests/run-z486-fuzz.sh`)
reduced the remaining failures to two instructions,
`mov eax,[uncached]; and eax,[ebp-12]`. An optimistic ROM read releases its
DLY in the dcache lookup cycle, and a VIPT successor may issue then. When the
read misses or is uncached, `mem_opt_wait` holds the sequencer but not the VIPT
EX/WB stage, which captured EAX from the memory token's stale OPR_R. Such an
EX op now takes the slow path (`vipt_load_ex_token_pending`). Deferred memory
and shift tokens also stay valid through stalls and recommit each cycle (this
delivers late OPR_R data, e.g. POP), so they now stop committing and
forwarding once a younger load WB wrote their register or a younger RMW-fast
step replaced OPR_R. A variant that committed tokens only once failed on a
lone POP and was discarded.

CS preservation fix (B149 hardware tested): CR0.PE entry now tracks CPL0 separately
from visible CS. The old code cleared the segment low bits, so HIMEMX at
058D:xxxx restored DS as058C and corrupted its own code during XMS resize.
A minimal all-four-low-bit regression fails on the old CPU; corrected
production RTL passes it and the captured resident HIMEMX resize with
19KB data comparison and unchanged driver code. On actual MiSTer, B149 passes
seven XMS resizes through 131KB, locks/unlocks and a data-copy round trip,
plus CPU/RAM64/FM/OPNA diagnostics. Doom now passes DX386 but exits later
with `R_GenerateLookup: alloca failure`; gameplay remains unconfirmed.
